# Model card: intent classifier

Generated by `python -m eval.model_card` from `eval/reports/intent_classifier.json` (run 2026-10-01T12:41:29) and `docs/evidence/model_study.json` (run 2026-10-01T04:49:46). Every figure below is read from those reports.

## What it is

A TF-IDF text classifier (char+word features: character 2-5-grams and word 1-2-grams) with a logistic regression (C = 10, balanced class weights), trained with scikit-learn 1.9.1 on 182 utterances. It labels a customer's message as one of six intents: `balance_inquiry`, `transaction_lookup`, `payment_status`, `exchange_rate_inquiry`, `out_of_scope` or `requires_escalation`.

## What it is used for, and what it must not be used for

At runtime it does two things before or around the language model (`agent/policy/intent_guard.py`), both deterministic given the model file:

1. **Escalation guard.** A message is handed to a person if the keyword lexicon fires **or** the probability of `requires_escalation` is at least 0.55 (a threshold chosen on dev for recall with false escalations at most 5%, never on test).
2. **Abstain or clarify.** When the model answers without calling a tool, its `out_of_scope` reading decides whether the reply is a refusal or a clarifying question.

It **does not decide outcomes, authorize actions or detect fraud.** Eligibility, routing and every side effect are code (`docs/decisions/ADR-001-model-interprets-code-speaks.md`, `docs/decisions/ADR-002-one-action-confirmed-in-code.md`). Using it as a fraud or risk score would be wrong: the fraud labels hold no learnable signal (`docs/decisions/ADR-005-no-fraud-or-risk-model.md`). If the model file is missing, both jobs fall back to keywords and the degradation is logged.

## Data

- **Training:** 182 utterances written by the team from templates (`eval/test_cases/intent_dataset.csv`, sha256 `b7c35dd8b895`). The keyword baseline's rules were written from the same templates.
- **Held-out:** 174 utterances written after the training data and the baseline were frozen, with deliberately different phrasing (regional slang, abbreviations, no accents, code-switching), plus 2 real request sentences from the dataset's transcripts. Split by a fixed hash into dev (88, used for selection and the threshold) and test (85, scored once). Phrases too close to the training text were left out by a leakage check.
- **No real customer text.** The organizer's transcripts hold 42 distinct customer texts (`docs/data_quality.md`), so every training and evaluation utterance except 2 was written by the team. We have no record of a native-speaker review of the Portuguese text.

## How it does (test split, scored once)

| | Keyword baseline | Learned |
|---|---|---|
| Accuracy | 63.5% [52.9%-73.0%] (n=85) | 84.7% [75.6%-90.8%] (n=85) |
| Macro-F1 | 0.6576 | 0.8485 |

On the same 85 utterances the learned classifier is right where the baseline is wrong on 26 and the reverse on 8: +21.2 points (paired bootstrap 95% [+8.2, +34.1], exact McNemar p = 0.002935).

**Escalation guard** (what actually runs before the model):

|---|---|---|
| lexicon_only | 86.7% [62.1%-96.3%] (n=15) | 0.0% [0.0%-5.2%] (n=70) |
| classifier_only | 46.7% [24.8%-69.9%] (n=15) | 0.0% [0.0%-5.2%] (n=70) |
| lexicon_or_classifier (runtime) | 93.3% [70.2%-98.8%] (n=15) | 0.0% [0.0%-5.2%] (n=70) |

The runtime guard missed 1 of 15 required escalations on test. A miss is a real missed escalation: the language model has no escalate tool (`eval/reports/intent_classifier.md` names the miss).

## Where it fails

- **Escalation is the weakest class on its own.** `requires_escalation` recall is 60.0% [35.8%-80.2%] (n=15) for the classifier alone, which is why it is only ever used together with the lexicon.
- **Out of scope** recall is 80.0% [54.8%-93.0%] (n=15): the baseline does better there, and some out-of-scope requests are read as another intent.
- **Portuguese is behind Spanish:** 80.6% [65.0%-90.2%] (n=36) against 86.7% [73.8%-93.7%] (n=45). The intervals overlap, so this is a gap we cannot prove and cannot rule out, and we have not separated its cause.
- **Slang:** 33.3% [6.2%-79.2%] (n=3). Three utterances: read it as a warning, not a rate.
- **Scored on text the team wrote.** Shared phrasing habits between training and held-out text can flatter both systems, so the figures are a ceiling for how it reads real customers, not an estimate of it.

## How much its design choices matter

A sensitivity study on dev only (`docs/evidence/model_study.md`, protocol fixed before it ran: the shipped model does not change). Of the 14 other representation and regularization settings, 11 are distinguishably worse than the shipped one on dev macro-F1 (0.9003) and the rest are within noise; none is better. The shipped configuration was chosen on that same dev set, so its row is the optimistic one. The learning curve is still rising at the end (0.8450 at 75% of the data, 0.9003 at 100%), which says that more text of the same kind, ideally written by people outside the team, is the lever.

## Reproducing it

- `make train-eval` rebuilds the dataset, trains, selects by template-grouped cross-validation on the training set plus dev and scores test once; it writes `eval/reports/intent_classifier.{md,json}` and the model.
- `python -m eval.model_study` re-runs the sensitivity study; `python -m eval.model_card` re-renders this card.
- With `requirements-tracking.txt` installed, every selection and evaluation run is also logged to MLflow (`make mlflow-ui`); the store is local and git-ignored.
- `make validate-data-ml` checks the data contracts, the split and the leakage controls as PASS/FAIL.
